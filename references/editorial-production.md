# 公众号成稿与视觉总编

## 选择文章深度

- `架构解释`：说明目的、主要组成、职责、关系、部署选择和用户/产品后果。研究可看源码，公开正文默认不写路径、类名、字段和命令。
- `公众产品或行业文章`：从具体人物、设备、场景和价值切入，只保留解释结果所需的技术机制。
- `开发者实操`：用户明确要求实现、源码、安装、测试或复现时，才加入代码、命令、环境与故障记录。
- `个人思考`：必须有真实第一人称场景、具体细节、由此产生的判断，以及与当前工作的连接。

技术深度服从读者问题。长文不等于源码文，工具主题也不自动等于教程。

## 编辑简报

写作前在内部形成：

- 主要读者与具体阅读时刻。
- 一个可回答的问题。
- 一句中心判断。
- 事实清单、来源和不可越过的边界。
- 一个主要读者动作。
- 内容形态与期望篇幅；篇幅默认是参考，只有用户给出明确范围并要求严格遵守时才是硬门禁。

先做删减判断：资料无法支撑的具体结论直接不写，不用免责声明包裹；读者不需要的实现细节移入证据卡或技术附录。

## 正文方法

- 尽早给出核心判断。首屏约 `120-180` 个汉字回答：这是什么、为什么现在值得关注、读者能得到什么、胡楠楠怎么看。
- 用 `事实 -> 解释 -> 对读者的后果` 推进。每一节承担一个新任务，不重复换词总结。
- 段落通常 1-3 句，但以真实文风和阅读节奏为准；长短句自然交替。
- 删除无意义、装饰性的状语和补语。保留时间、条件、范围、程度和结果所需成分。
- 少用抽象商业词和万能句式；能说清对象、动作、条件与结果时，不用“赋能、闭环、抓手、重塑、未来已来”等口号。
- 不机械排比、不滥用三段式、加粗、小标题和“不是 X，而是 Y”。必要对比可以写，但不要把全文写成同一种句型。
- 不强行制造完美结构。允许有真实停顿、犹豫和复杂判断，但不能用松散代替逻辑。

## 标题系统：内部 8 选 1

正文中心判断稳定后生成恰好 8 个候选，覆盖至少四种机制：

1. 直接收益或决策。
2. 冲突、反差或误判。
3. 具体读者问题或痛点。
4. 当下变化、具体场景或真实故事。

候选必须真正换角度，不能只换同义词。内部按五项等权判断：读者识别、具体性、张力、实用/转发价值、证据与正文匹配。保留 3 个，确定 1 个；只有用户要求时才展示候选，评分过程不进入文章。

标题规则：

- 主要对象或冲突放在前半段，通常控制在 `14-28` 个汉字，尽量不超过微信标题上限。
- 每个名称、数字、时间、价格、排名、速度、结果、引语、排他性和第一人称声明都能追溯到当前证据。
- 新项目可测试 `时间 + 跨过的稳定里程碑 + 读者可见结果`，但增长信号必须有创建/发布时间、指标时间和来源。没有完整时间证据时改用痛点或行动方向。
- 问句必须在正文明确回答；承诺 N 点就交付 N 个不同内容；结果型标题要说明条件与边界。
- `终于、第一次、爆火、疯传、颠覆、所有人都在` 只有在事实与机制都支持时使用。
- 标题的承诺须在首屏兑现。无法干净兑现时，削弱标题，而不是在正文后面补免责声明。

## 正文检查点与事实审查

排版、生图前先形成完整正文检查点，包含标题、摘要、正文和最终 HTML 将出现的全部实质可见文字。短编号和纯导航标签可在排版时添加，新的结论、参数标签、免责声明和引导语不可以。

逐条核对：

- 产品分类不等于产品功能；平台支持不等于具体产品已实现。
- 最高值、峰值、理论值、标称值与实测值不能混用。
- 两个事实同时存在，不等于已证明因果。
- “避免、提升、带来、保证、足够、第一时间、必然”等效果词必须有条件与证据。
- `未提供` 不能改写成 `不具备`；`计划` 不能改写成 `已经完成`；`研究` 不能改写成 `实测`。
- 修改正文后，旧审查结论失效，必须针对当前版本复查。

事实门禁无法完成时，交付 `待人工核对` 的正文，不声称通过，也不继续创建公众号草稿。

## 原创与作者识别

研究型文章至少需要：

- 一项第一方贡献：真实测试、截图、计算、客户场景、产品决策或工程判断。
- 两个一手来源（可获得时）。
- 一个解释 why、边界或商业意义的非显然判断。
- 一个读者当天可使用的命令、清单、模板、流程或决策规则。
- 两个删除作者名字后仍能识别为胡楠楠视角的元素。

使用 `assets/originality_audit.md`。没有通过就继续研究或缩小命题，不靠扩写凑成文章。

## 配图与视觉方向

优先使用用户原图、官方实物图、产品截图、真实输出或来源明确的图。原图足够时不机械补图。生成图用于封面、概念、情绪或机制解释；必须标明概念性质，不能替代产品证据或伪装成实拍。

写 HTML 前锁定一个视觉方向：

- `intent`：一句编辑意图。
- `theme`：深或浅。
- `canvas / ink / muted / accent`：整页底色、主文字、弱文字和强调色。
- `headline`：衬线或无衬线逻辑。
- `image rhythm`：通栏、内收或混合。
- `corner`：利落或柔和。
- `rhythm`：首屏、中段、转场和结尾的节奏描述。

方向由本篇读者、主题和品牌气质决定，不给同一套组件换颜色。产品发布、技术解释、人物故事和个人思考应形成不同的视觉重心。只有用户主动选择常用样式或固定模板时才继承对应标准。

## 排版预检

检查最终可交付的微信安全 HTML，而非只看源 CSS：

- 整页落实既定底色、主文字色和强调色。
- 主文字及摘要/图注与背景对比度至少 `4.5:1`；长文主文字尽量接近 `7:1`。
- 长段正文不低于 `15px`，行高不低于 `1.65`；通常正文 `16-17px`、行高约 `1.8-1.9`。
- 首屏只有一个主要焦点。标题与摘要不机械复述，正文不再重复 H1。
- 连续 5 个以上纯正文段，或约 760 字符没有图片、引语、章节转场时，检查是否节奏单一；这是编辑提醒，不是机械插图指标。
- 长文至少形成三种有意义的节奏元素，例如章节、图片、引语、清单/表格、重点模块；不要为了凑类型增加装饰。
- 修复阻断问题；审美建议只做一轮有实质变化的整页优化。不追逐虚构评分，不把网页预览声称为微信实机验收。

需要长文细则或与历史文章保持连续性时，再读 `references/longform-editorial-standard.md`。
